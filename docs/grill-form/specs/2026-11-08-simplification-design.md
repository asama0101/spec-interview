# grill-form を必要最低限に簡素化する SPEC

## 概要

grill-form は、計画や設計を、ブラウザのフォームに答えながら詰めて、SPEC 1 ファイルにまとめる Claude Code 用のプラグインである（Windows 11 専用）。エラーハンドリングや周辺機能が積み重なり、本体約 1,630 行・テスト約 1,575 行に膨らんだ。本質でない機能を手放して、プラグインがやりたいことだけを残す。

調査の記録は [簡素化のための調査](../../2026-11-08-simplification-survey.md)。

### プラグインがやりたいこと

1. Claude が grilling の考え方で質問を作り、フォームで出す。利用者は、選択・コメント・保留・聞き返しで答える。
2. 送信を自動で検知して、回答を Claude に渡す。
3. 決めることがなくなるまで、ラウンドを繰り返す。
4. SPEC 案を最終確認して承認する。承認したら、SPEC を 1 ファイル保存する。

## 最優先事項: grilling の考え方

質問の出し方は grilling に従う。次の 4 点はすべて外せない。SKILL.md の「ルール」節は、削る対象から外し、内容を変えない。

1. 決定を design tree として扱い、前提が決着済みの質問（frontier）だけを、1 ラウンドにまとめて出す。
2. 各質問に推奨案と理由を付ける。「はい」で受け入れられる文言にする。
3. 調べれば分かる事実は調べて、人には決定だけを聞く。
4. 聞き返しや保留を残さず、すべての枝をたどり終えるまで続ける。

手放す機能を決める基準は、「grilling の質問を妨げないか」とする。

## ゴール

- 上の 4 つの流れと grilling の 4 点が、手放したあとも同じように動く。
- コード・手順書・文書が、手放した機能の分だけ小さくなる。
- 残す機能のテストは、現状の方針のまま通る。

## 非ゴール

- 新しい機能を足さない。
- 残す機能の振る舞いを変えない（grilling の質問の出し方を含む）。
- Windows 11 以外への対応。
- 過去の spec と plan（`docs/grill-form/specs/` と `plans/` の既存ファイル）は変更しない。

## アンチゴール（動いても失敗とみなす）

- grilling の 4 点のどれかが弱まる。
- 手放すと決めた機能の残骸（未使用の関数、手順の参照、README の記述、テスト）が残る。
- 簡素化を理由に、残すと決めた機能が壊れる。

## 残す機能

| 機能 | 補足 |
| --- | --- |
| 質問フォーム | 選択・コメント・保留・聞き返し、「選択をクリア」。未回答の警告（1 回目の送信で警告し、もう一度押すと送る）を残す |
| 簡易 Markdown | 質問の `body` で使う。段落・箇条書き・コードブロック・インラインコード・表・折りたたみ。まず現状のまま残し、削れるかは実装で見る |
| 送信の自動検知 | Playwright MCP の `browser_evaluate` で待つ |
| ラウンドの繰り返し | frontier が空になるまで。「保留・聞き返しが残る間は SPEC 案に進まない」の 1 行を、点検 1 の代わりに SKILL.md に残す |
| 最終確認 | 承認 / 修正あり。修正のたびに版を上げる |
| 5 体のクロスレビュー | SPEC 案を出す前に、会話を持たないサブエージェント 5 体で確かめる。手順は現状のまま |
| 入力フォーム（依頼文のテキスト入力欄だけ） | 下の「入力フォーム」を参照 |
| `doctor` | 新しい PC への初期導入で使うので残す。中身を軽くできるかは、ビルダーの判断に任せる |
| SPEC の保存 | 概要・流れ・受入条件・非目標・リスク・決定ログ。保存先と連番付けは現状どおり |
| テスト | 現状の方針。消す機能のテストは消し、残す機能のテストは保つ |

### 入力フォーム

最初の画面は、依頼文のテキスト入力欄と「送信」だけの 1 画面にする。起動時にテーマが一緒に送られていれば、その原文を欄に入れておく（現状の `--input` による転記は残す）。依頼文が空のフォームは送信できない。

参考資料は、利用者が依頼文の本文にパスを書き、Claude が元の場所のまま読む。読み方（PDF・Word・PowerPoint・Excel のスキルの使い分け）は現状の記述を引き継ぐ。パスの存在確認は、現状の記述（存在しない・フォルダなら再入力を求める）を引き継ぐ。手順 2 末尾の「ユーザーが入力不要と言ったときだけ、入力を省略できる」も残す（振る舞いを変えないため）。

回答 Markdown（入力フォーム）は、frontmatter を `intake: 1` のまま残し、本文は `## 依頼文` の 1 節だけにする。`- 種別:` の行と `## 参考資料` の節はなくす。手順 9 の概要の「入力」に書く参考資料のパス一覧は、依頼文の本文から Claude が拾う。

## 手放す機能

| 手放す | 一緒になくなるもの |
| --- | --- |
| 参考資料のツリー選択 | ファイル一覧、Shift 範囲選択、チェックの保持、パス欄の優先ルール、「フォルダを読み直す」、`folder_scan.py` と `test_folder_scan.py`、`render --intake` のツリー埋め込み、`--answers`（状態の復元）、`parse_intake_answers` |
| 依頼文の「ファイル」指定 | 依頼文の種別の切り替え、回答の `## 保留の依頼文` |
| セッションの再開 | 手順 0（一覧と選択肢）、再開の判定表、`list`、14 日掃除（`prune_old`、`prunable`）、cwd 照合（`belongs_here`）、`describe_session`・`newest_file`・`mtime_of`・`one_line`、`session.json`、README の「中断したセッションを再開する」 |
| 作業ファイルの削除の仕組み | `cleanup`（三重ガード）、手順 10 の `cleanup` の実行。作業ファイルは OS の一時フォルダに置いて、掃除は OS に任せる |
| Round 0 | 手順 3、SPEC への吸収ルール。目的・障壁・制約は、通常の質問として frontier に出る |
| 点検 1 | 手順 8 の 4 項目。「保留・聞き返しが残る間は SPEC 案に進まない」の 1 行だけ手順 8 に残す。手順 9 の「点検 1 からやり直す」「点検 1 が通ったら」は、「手順 8 に戻る」「frontier が空になったら」に置き換える。ぶれる言葉・要求の網羅・完了基準の 3 項目は、クロスレビューの観点 1 と 3 に任せる |
| SPEC の `status`・`plan` | frontmatter、末尾の「後続の手順」、計画パスの命名規則。SPEC は本文だけにする |
| 中止ボタン | 2 回押し、回答の `## 中止`。待機中の中止は、ターミナルへの入力で行う |
| 質問一覧の帯 | 画面上部の番号・状態の印・件数・クリック移動 |

## 制約

- Windows 11 専用。Python は標準ライブラリだけで動かす（3.8 以上）。
- 質問の JSON の形式（`id`・`title`・`body`・`multi`・`options`・`recommended`・`reason`）は変えない。grilling の質問を、そのまま出せるようにするため。
- 回答 Markdown は、質問ごとの `選択`・`コメント`・`聞き返し`・`状態` を保つ。
- 利用者のルール（`~/.claude/rules/`）に従う。Python は ruff が通ること、`encoding="utf-8"` を明示すること、README は利用者向けに書くこと。
- バージョンは、`grill_form.py` の `__version__` と `plugin.json` で一致させる。再開と中止がなくなる破壊的変更なので、`2.0.0` に上げる。版を上げるのは、これまでの履歴（#15・#17）と同じく、機能の変更とは別のコミット（別の PR）にする。

## 作業フォルダの置き場

作業用ファイル（質問 JSON、HTML、回答）の置き場は、OS の一時フォルダ配下とする（`${CLAUDE_PLUGIN_DATA}` ではない）。フォルダの作り方と名前は、ビルダーに任せる。SPEC は、現状どおり作業フォルダの `docs/grill-form/specs/` に保存する。

## ビルダーに任せること

- 作業用フォルダの具体的な作り方（`init` を残すか、スキルが直接作るか）。
- `doctor` の軽量化の範囲。
- `allowed-tools` の `python` と `python3` の重複の整理。
- 簡易 Markdown のうち、削れる部分。
- テストの具体的な削り方（消す機能のテストを消し、残す機能は保つ）。
- README・開発メモ（`docs/development.md`）の書き直し。手放す機能の記述を消し、機能数・コマンド名・フラグをコードと照合する。

## 受入条件

1. `pytest`・`ruff check`・`ruff format --check` が通る。
2. SKILL.md の「ルール」節の内容が、変更前と同じである（`git diff` で確認できる）。
3. 手放す機能の名前が、機能名として本体・SKILL.md・README・開発メモ・テストから消えている（`grep` で確認できる）。対象は `folder_scan`、`cleanup`、サブコマンドの `list`、`prune_old`、`Round 0`、`点検 1`、`status:`、`plan:`、「中止ボタン」、`## 中止`、`session.json`。一般語としての「中止」「list」は対象外（待機中にターミナルへ入力して止める旨の記述は残す）。過去の spec と plan も対象外。
4. 質問フォームを 1 ラウンド開き、回答を送信し、承認まで進んで SPEC が保存される。ビルダーが Playwright MCP で実際に操作して確かめ、結果を報告する。
5. 本体（`grill_form.py`・`grill_form_template.html`・SKILL.md 2 本）の行数が、約 1,630 行から減っている。目標の数字は置かない。

## リスク

- 参考資料のツリー選択をなくすと、作業フォルダ内のファイルを探す手間が増える。パスを本文に書く形で補う。
- 一時フォルダに置くため、中断した作業は再開できず、OS の掃除まで一時フォルダに残る。回答に秘密情報を書いたときの扱いを README に書く。
- Round 0 をなくすと、目的・障壁・制約が質問に出ない場合がありうる。grilling の frontier が、これらを通常の質問として拾うことを前提にする。

## 決定ログ

| 項目 | 決定 | 理由 |
| --- | --- | --- |
| 最優先事項 | grilling の 4 点 | 利用者の指示 |
| 参考資料のツリー | 手放す | 依頼文だけで十分と、利用者が回答 |
| 再開 | 手放す | 実際に使っていない |
| Round 0 | 手放す | 利用者の判断。通常の質問で足りるとみる |

| `status`・`plan` | 手放す | 利用者が不要と回答 |
